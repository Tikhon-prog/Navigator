# Глубокий аудит проекта «Поколение» — 11 ноября 2026

## Статус и границы проверки

Это ревизия исходников и конфигурации ветки `work/docker-dev-environment`, а не акт приёмки готового школьного продукта. GitHub Actions, удалённые сборки и публикации не запускались. В этой среде не выполнялись Flutter/Python-тесты, `flutter analyze`, Docker image build и APK/EXE build. Поэтому новые изменения ещё должны пройти локальную проверку на компьютере разработчика.

Проверка охватывала Flutter-клиент, локального ИИ, маршрутизацию, FastAPI backend, RBAC/SSO, уведомления, Android toolchain, Docker-конфигурацию и документацию.

## Архитектура, которая уже есть

- Flutter-клиент с офлайн-картами трёх этажей, каталогом помещений, графом коридоров, маршрутизацией, расписанием, ДОПами, заметками, заданиями и локальными напоминаниями.
- Локальный Qwen 2.5 0.5B Instruct GGUF, который скачивается отдельно от приложения и вызывает инструменты клиента. Маршрут вычисляет детерминированный графовый движок, а модель интерпретирует запрос и передаёт параметры.
- Отдельный FastAPI backend с SQLite, серверными сессиями, OIDC SSO, должностями/правами, назначениями учеников, ДОПами, аудитом и уведомлениями.
- Набор Flutter unit/widget тестов и Python backend regression tests. Сами тесты присутствуют в репозитории; их успешный проход в рамках этого аудита не подтверждался.

## Исправления в этой ветке

1. **RBAC и руководство школы.** Закрыта возможность для директора/заместителя изменять аккаунт другого директора/заместителя через управление персоналом. Добавлена защита от отключения или снятия должности последнего активного директора. Добавлены шесть регрессионных тестов в `backend/tests/test_rbac_api.py`. Они добавлены, но ещё не запускались.
2. **Удаление через локальный ИИ.** Удаление локального ДОПа или задания теперь останавливается на отдельном диалоге подтверждения. При отмене обработчик не выполняет удаление.
3. **Версия приложения.** `pubspec.yaml` приведён к `0.2.0+2`, чтобы Android versionCode был 2, как ожидают release notes и документация. Release script проверяет наличие build number.
4. **Подпись APK.** Существующий debug-key fallback оставлен для локального тестирования, но сборочные скрипты теперь явно предупреждают, что такой APK не предназначен для production-распространения.
5. **Размер Flutter asset bundle.** Удалены из списка Flutter assets исходные `.xlsx`, PDF и PNG-планы. Они остаются в Git как материалы для разработки, но код приложения ссылался только на оптимизированные `floor1.webp`–`floor3.webp`. Исключённые исходники занимали около 49 MiB без учёта сжатия APK; фактический размер нового артефакта нужно измерить после локальной сборки.
6. **Среда разработки.** Добавлен отдельный Docker Compose профиль с закреплёнными версиями Flutter/Dart, JDK, Android command-line tools и Python dependencies, кешами и командами локальной проверки/Android APK.

## На что обратить внимание до распространения

### 1. Офлайн-расписание

`assets/data/school_schedule_2026-10-05.json` содержит варианты занятий для 33 классов и 1 866 записей-вариантов; поля включают предмет, группу, день, время, кабинет и учителя. Файл включён в клиент для офлайн-режима, поэтому его можно извлечь из APK/EXE. Закрытый GitHub-репозиторий не защищает эти данные после распространения приложения. Нужна явная авторизация школы на такой офлайн-состав; более изолированная схема — загружать после входа только разрешённый класс и хранить его локальный кеш.

Исходная Excel-таблица остаётся в репозитории для разработки, но исключена из Flutter asset bundle вместе с исходными картами. Это сокращает упаковку, однако не удаляет сам расписной JSON из клиента.

### 2. Физическая проверка маршрутов

Тесты доказывают связность графа и отсутствие некоторых дубликатов сегментов. Они не доказывают, что каждый отрезок совпадает с физически проходимым коридором на утверждённом плане. Документ `ROUTING_AUDIT.md` уже описывает спорные соединения около кабинетов 315–318 и необходимость визуального сравнения с оригиналом. До такой сверки нельзя представлять маршруты как утверждённые маршруты эвакуации. Нейросеть не должна придумывать геометрию пути; она может понимать запрос пользователя, но поиск пути должен оставаться детерминированным по проверенному графу.

### 3. Совместимость Android toolchain

Текущая связка в исходниках: Gradle 9.9.0, Android Gradle Plugin 9.1.1, Kotlin Gradle Plugin 2.4.21, JDK 27. AGP 9.1.1 требует Gradle не ниже 9.3.1, поэтому минимальное требование AGP выполнено. Но таблица Kotlin указывает полный диапазон поддержки KGP 2.4.20–2.4.21 до Gradle 9.7.0; 9.9.0 находится выше полностью проверенного диапазона. Это не доказывает ошибку сборки, но является конкретным риском совместимости: первым делом проверь Android APK на локальной машине и при проблемах согласуй версии Gradle/Kotlin/AGP, а не меняй их вслепую.

Флаги `android.builtInKotlin=false` и `android.newDsl=false` соответствуют описанному Flutter переходному режиму для старого Kotlin plugin/DSL на AGP 9. Flutter рекомендует перейти на built-in Kotlin после миграции приложения и всех используемых plugins. Это отдельная задача, не выполненная в данном аудите.

Источники:
- Kotlin Gradle compatibility: https://kotlinlang.org/docs/gradle-configure-project.html
- Android Gradle Plugin 9.1.1 requirements: https://developer.android.com/build/releases/agp-9-1-0-release-notes
- Flutter migration to built-in Kotlin: https://docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin

### 4. Подпись Android

Пока `android/key.properties` отсутствует, release build использует локальный debug keystore. Это удобно для тестирования, но не годится для нормального обновляемого релиза. До распространения нужно создать отдельный постоянный release keystore, хранить его вне Git, настроить `android/key.properties` только локально/в секретном хранилище и обеспечить резервную копию ключа. Не публикуй APK, подписанный debug-ключом, как production.

### 5. Серверная интеграция не равна подключению к школьной системе

Backend и адаптеры данных реализованы, но реальное подключение требует утверждённой схемы источника, HTTPS API/JSON, OIDC issuer/client/redirect URI, bootstrap-администратора, постоянного SQLite volume, резервного копирования и при необходимости Firebase. Сопоставление реальной intranet-схемы и разрешений остаётся работой школьного IT. Наличие кода не означает, что учётные записи, расписание или push уже синхронизированы с системой школы.

### 6. Локальный ИИ и реальные устройства

Модель Qwen 2.5 0.5B хранится отдельно от базового приложения и запускается с `nGpuLayers: 0` и контекстом 4096 токенов, то есть текущая конфигурация рассчитывает на CPU. Размер файла модели — около 491 MiB. Это не подтверждает приемлемую скорость, расход памяти или точность вызова инструментов на любом Android-телефоне/старом ноутбуке: нужны замеры на реальных целевых устройствах. Для маршрутов модель должна только понимать запрос и параметры; сам путь рассчитывается детерминированным движком по проверенному графу.

### 7. Воспроизводимость backend

Flutter-зависимости закреплены в отслеживаемом `pubspec.lock`. Python-зависимости в `backend/requirements.txt` заданы диапазонами версий, а не полным lock-файлом с хешами. Поэтому повторная сборка Docker-образа в будущем может получить более новые версии библиотек внутри этих диапазонов. Перед долгоживущим production-развёртыванием стоит создать lock-файл Python-зависимостей с контрольными хешами и обновлять его контролируемо.

### 8. Web/PWA и сетевые ограничения

Backend по умолчанию допускает CORS origin `*`, если `NAVIGATOR_ALLOWED_ORIGINS` не задан; в примере серверной конфигурации предусмотрен явный origin. До публикации PWA нужно указать точные разрешённые адреса сайта. Текущий login throttling хранится в памяти процесса, поэтому он не заменяет централизованное ограничение запросов при нескольких workers/экземплярах. В документации серверной интеграции это уже отмечено как production-ограничение.

### 9. Структура клиентского кода

`lib/main.dart` остаётся очень большим файлом, в котором собраны маршрутизация, данные школы, навигационный экран и обработчики локального ИИ. Это усложняет безопасные изменения и ревью. Не стоит делать массовый перенос в рамках короткого исправления; лучше выделять независимые сервисы/модули небольшими шагами, сопровождая каждый перенос тестами.

## Рекомендуемый порядок локальной проверки

1. Открыть ветку `work/docker-dev-environment` на библиотечном Windows-компьютере или в Lubuntu/Docker Engine.
2. Выполнить `python backend/security_check.py` и `python -m unittest discover -s backend/tests -v`.
3. Выполнить `flutter pub get`, `flutter test` и `flutter analyze --no-fatal-infos --no-fatal-warnings`.
4. Собрать Android APK и сравнить итоговый размер с предыдущим. Проверить установку поверх тестовой версии и отдельно проверить подпись.
5. Сверить маршруты 311→317, 311→316 и вход→этажи по актуальному утверждённому плану.
6. До подключения реальных учеников получить одобрение школы на локальный снимок расписания, роли, SSO и политику уведомлений.

Этот список — именно следующий этап проверки, а не заявление о выполненных тестах или готовности production.
