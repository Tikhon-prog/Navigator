## 1. Назначение и границы системы

«Поколение» — приложение для школьной навигации и расписания. Основной сценарий рассчитан на работу на устройстве без постоянно доступного интернета: карты, точки помещений, геометрия маршрутов и некоторые данные расписания поставляются в составе приложения.

Сервер — отдельная, необязательная часть. Он нужен для школьных аккаунтов, управляемых назначений сотрудников и учеников, индивидуальных записей дополнительных занятий, аудита, синхронизации и расширенных уведомлений. Сборка клиентского APK не разворачивает сервер и не создаёт настоящие аккаунты.

**Компоненты:**

- **Flutter-клиент:** интерфейс и локальные сценарии на Android/Windows; в репозитории присутствует iOS-конфигурация и соответствующие CI workflow.
- **Локальные ресурсы:** планы этажей, комнаты, узлы дверей/коридоров, маршруты и снимок расписания.
- **FastAPI backend:** публичный read-only доступ к согласованным справочникам и отдельный API `/api/v2` для авторизованных операций.
- **SQLite:** учётные записи, сессии/refresh tokens, связи с SSO, назначения сотрудников и учеников, индивидуальные ДОПы, зарегистрированные устройства, аудит и уведомления.
- **Внешние школьные сервисы:** OIDC-провайдер, источник расписания/справочников и, при необходимости, Firebase. Эти сервисы требуют отдельной настройки и не включены автоматически.

## 2. Функциональность

### 2.1 Клиентские функции, описанные в исходниках и README

- Планы первого, второго и третьего этажей с масштабированием, панорамированием и полноэкранным просмотром.
- Поиск кабинетов по номеру/названию и построение маршрута по графу коридоров с пошаговыми подсказками.
- Локальное расписание и каталог расписания по классам, выбор учебной группы там, где она задана в данных.
- Обратный отсчёт до конца урока или перемены на основе расписания выбранного класса.
- Раздел дополнительных занятий (ДОПы), разбор доступных данных портала, отображение нужного кабинета и локальные напоминания, когда известно время занятия.
- Объявления, офлайн-кеш ленты и локальные уведомления.
- Личные заметки с созданием, редактированием и удалением. В README заявлено локальное хранение на устройстве и разделение по школьному аккаунту.
- «Кабинет школы» для ученика и сотрудников; клиент показывает интерфейс согласно доступным разрешениям, но окончательное решение о доступе принимает сервер.

### 2.2 Серверные функции

- Вход локальным логином/паролем для техучётной записи по настроенным правилам; школьный вход через OIDC.
- Access-/refresh-сессии, ротация refresh-токенов и завершение сессии.
- Учётные записи, активность аккаунта, связи ученика с профилем, привязка SSO-идентичностей.
- Разделение базовой роли аккаунта и школьной должности/назначения.
- Явные назначения учителей на предметы и наставников на учеников; нельзя безопасно выводить эти отношения только из имени или класса.
- Синхронизация индивидуальных ДОПов и назначений, операции сотрудников с разрешённым охватом данных.
- Общешкольные, классные, групповые и личные уведомления; настройка пользовательских предпочтений.
- Журнал аудита и состояние синхронизации.
- Необязательная push-доставка Firebase Cloud Messaging на поддерживаемых мобильных платформах.

Наличие endpoint или раздела интерфейса не заменяет сценарное тестирование в окружении школы. Перед объявлением функции готовой проверяй все роли, крайние случаи и ошибки сети.

### 3.3 Поток данных

1. Офлайн-функции клиента читают поставленные в APK assets.
2. При настроенном сервере клиент обращается к заданному API URL.
3. Публичные справочники получают данные из настроенного источника JSON/HTTPS; эти операции предназначены только для чтения.
4. Защищённые операции проходят проверку серверной сессии, базовой роли, должности и явного назначения/охвата.
5. Персональные и управляемые данные хранятся в SQLite backend, а не в публичном JSON-справочнике.
6. Push-доставка запускается отдельно и требует собственных server credentials и клиентских настроек.

## 4. Требования к среде

### Android / Flutter

- Flutter stable **3.47.4** — версия, указанная в README и сценарии сборки.
- Dart SDK, входящий в подходящую Flutter-сборку; в `pubspec.yaml` диапазон SDK: `>=3.10.0 <4.0.0`.
- Android SDK и лицензии платформ.
- JDK 21. В Gradle-конфигурации Java/Kotlin toolchain настроен на 21; не подменяй его случайно более новой системной JDK без проверки Gradle/AGP.
- Интернет и место под SDK/зависимости. Скрипт автоматической установки рекомендует около 25 ГБ свободного места.

### Windows desktop

- Windows 10/11 x64.
- Visual Studio 2022 или Build Tools с workload **Desktop development with C++**, Windows SDK и ATL.
- Inno Setup 6 — если собирается установщик из `windows/installer.iss`.

### Backend

- Python 3.12 или новее (такой минимум указан в серверном README).
- Базовые пакеты из `backend/requirements.txt`.
- Доступный файл школьных данных либо HTTPS endpoint источника.
- Для production: сервер/контейнер, постоянный том для SQLite, HTTPS reverse proxy, резервное копирование, логи и мониторинг.
- Для SSO — согласованные школой OIDC issuer/client/redirect URI.
- Для push — проект Firebase, Android app settings и service-account credential на сервере.

Все команды запускаются из корня репозитория.

```powershell
flutter pub get
```

На Linux/macOS команды аналогичны, с учётом установленного toolchain. Если анализ сообщает предупреждения, фиксируй причины; флаги `--no-fatal-*` позволяют не превращать некоторые предупреждения в немедленный отказ команды, но сами предупреждения не устраняют.

### 5.2 Собрать Android APK

Для быстрой сборки/debug-установки:

```powershell
flutter build apk --debug
```

Для release-варианта:

```powershell

```

При сборке напрямую Flutter стандартный APK лежит в `build/app/outputs/flutter-apk/`. Скрипт `setup_and_build.ps1` собирает и копирует файлы в отдельный каталог распространения, описанный в [BUILD_INSTRUCTIONS.md](BUILD_INSTRUCTIONS.md).

### 5.3 Собрать Windows desktop

На Windows с установленными Visual Studio C++ Build Tools:

```powershell

```

### 5.4 Автоматическая установка на чистой Windows

Из доверенного PowerShell/Windows Terminal следуй сценарию в [BUILD_INSTRUCTIONS.md](BUILD_INSTRUCTIONS.md). Там приведена команда скачивания и запуска `setup_and_build.ps1`. Скрипт настраивает инструменты сборки, запускает проверки и собирает клиент; он **не** создаёт школьные аккаунты, не настраивает OIDC, не разворачивает backend, не получает закрытые данные расписания и не генерирует Firebase service-account.

Перед запуском удалённого скрипта изучи его содержимое и источник. Скрипт требует интернета, иногда прав администратора и заметного объёма диска.

## 6. Сервер: запуск и развёртывание

### 6.1 Быстрый локальный запуск без Docker

Из корня репозитория:

```powershell
python -m pip install -r backend/requirements.txt
Copy-Item .env.example .env
```

Затем заполни необходимые поля в `.env`: прежде всего реальный `NAVIGATOR_TOKEN_SECRET`, `NAVIGATOR_DB_PATH`, настройки источника данных и при необходимости учётную запись bootstrap admin. Не запускай сервер для реальных пользователей с `CHANGE_ME`.

Подготовь файл данных по разделу 8 и укажи путь в `NAVIGATOR_DATA_JSON_PATH`. Затем:

```powershell
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Локальная проверка health:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
Invoke-RestMethod http://127.0.0.1:8000/api/v2/health
```

При доступности схемы FastAPI можно просмотреть документацию API разработчика по адресу `http://127.0.0.1:8000/docs`. Это вспомогательная документация интерфейса, а не замена настоящей аутентификации и проверки прав.

### 6.2 Запуск с Docker Compose

```powershell
Copy-Item .env.example .env
# Отредактируй .env: secrets, path источника и другие параметры
docker compose up --build -d
docker compose logs -f navigator-api
```

Compose хранит SQLite в named volume `navigator_data` и публикует порт как `127.0.0.1:8000:8000`. Это намеренно локальная публикация: наружу API должен идти через HTTPS reverse proxy, который настроен отдельно.

**Важный нюанс JSON-файла:** существующий `docker-compose.yml` монтирует named volume в `/data`, но не bind-mount отдельный файл `school-data.json` из рабочей папки хоста. Поэтому одного значения `NAVIGATOR_DATA_JSON_PATH=/data/school-data.json` недостаточно: файл должен действительно присутствовать по этому пути внутри контейнера. Подготовь способ доставки файла в volume либо добавь проверенный read-only bind mount в Compose. Для внешнего сервиса укажи `NAVIGATOR_DATA_SOURCE=http` и корректный HTTPS URL.

Healthcheck Compose обращается к `/api/v2/health`. Проверяй логи контейнера, доступность источника данных и сохранность тома после пересоздания контейнера.

### 6.3 Обслуживание

- Храни SQLite на постоянном томе и регулярно делай зашифрованные резервные копии.
- Проверяй восстановление копии, а не только факт создания backup.
- Перед обновлением кода останови/переключи трафик по принятой процедуре и сохрани копию базы.
- Используй один экземпляр сервера/worker, если не проверена корректность конкурентной отправки уведомлений и синхронизации. В коде есть защита состояния задач, но это не освобождает от нагрузочного тестирования.
- Включай внешний мониторинг доступности и ошибки API; не записывай токены/пароли в логи.

## 7. Переменные окружения

Полный перечень имён содержится в [.env.example](../.env.example) и [backend/.env.example](../backend/.env.example). Примерные значения нужны как шаблон: не применяй их без замены. Корневой `.env.example` — рекомендуемая отправная точка.

| Переменная / группа | Назначение | Рекомендация |
|---|---|---|
| `NAVIGATOR_SCHOOL_NAME` | Отображаемое название школы для серверной части | Укажи утверждённое название |
| `NAVIGATOR_TOKEN_SECRET` | Подпись серверных access-токенов | Случайное значение не короче 32 символов; секрет только на сервере |
| `NAVIGATOR_DB_PATH` | Путь к SQLite | Должен быть доступен на запись и находиться на постоянном томе |
| `NAVIGATOR_TOKEN_TTL_SECONDS` | Время жизни access token; пример — 28800 секунд | Меняй с учётом модели риска |
| `NAVIGATOR_REFRESH_TTL_SECONDS` | Жизнь refresh token; пример — 2592000 секунд | Используется с ротацией, продумай отзыв сессий |
| `NAVIGATOR_BOOTSTRAP_ADMIN_USERNAME/PASSWORD` | Первичная техническая админ-учётка | Пароль минимум 14 символов; bootstrap создаётся только при отсутствии администратора |
| `POKOLENIE_BOOTSTRAP_DIRECTOR_*` | Необязательное создание первого директора и имя отображения | Только после подтверждения полномочий; пароль минимум 14 символов |
| `POKOLENIE_BOOTSTRAP_DIRECTOR_SSO_SUBJECT` | Привязка стабильного OIDC `sub` директора | Только вместе с настроенным OIDC и после проверки личности школьным IT |
| `NAVIGATOR_ALLOW_NON_SSO_PASSWORD_LOGIN` | Разрешение локального password login не для админов | По умолчанию `false`; не включай без явного согласования |
| `NAVIGATOR_ALLOWED_ORIGINS` | Разрешённые browser origins для CORS | Укажи реальные origin; не используй wildcard без обоснования |
| `NAVIGATOR_OIDC_*` | Конфигурация школьного OIDC и имена claims | Получить у школьного IT; не угадывать issuer/claims |
| `NAVIGATOR_OIDC_AUTO_LINK_USERNAME` | Автоматическое связывание учётки по username | По умолчанию выключено; только при доверенном неизменяемом claim |
| `NAVIGATOR_OIDC_AUTO_PROVISION` | Автоматическое создание учётных записей | По умолчанию выключено; требует строгой проверки claims |
| `NAVIGATOR_OIDC_ALLOW_ADMIN_PROVISION` | Разрешение OIDC-провижининга администраторов | По умолчанию выключено; не включай без угроз-модели |
| `NAVIGATOR_DATA_SOURCE` | `json` или `http` | Явно выбери источник и проверь формат ответов |
| `NAVIGATOR_DATA_JSON_PATH` | Путь к JSON-файлу со справочниками | Путь должен существовать в среде процесса/контейнера |
| `NAVIGATOR_DATA_API_URL/TOKEN` | URL и необязательный Bearer token удалённого источника | Только HTTPS для удалённого источника; token хранить как секрет |
| `NAVIGATOR_NOTIFICATION_WORKER_ENABLED` | Включение фонового worker уведомлений | Проверяй интервалы и поведение после ошибки провайдера |
| `NAVIGATOR_NOTIFICATION_POLL_SECONDS` | Интервал обработки очереди на сервере | Настраивай с учётом нагрузки |
| `NAVIGATOR_AUTO_SYNC_INTERVAL_SECONDS` | Интервал синхронизации расписания/ДОПов/назначений; `0` отключает периодическую синхронизацию | Проверяй источник, логи и эффект изменения данных |
| `NAVIGATOR_SCHOOL_TIMEZONE` | Часовой пояс серверных напоминаний; пример `Europe/Moscow` | Укажи часовой пояс школы, проверь переходы времени |
| `NAVIGATOR_ENABLE_FIREBASE` | Включает зависимость и путь Firebase push | По умолчанию `false`; после включения пересобери Docker image |
| `FIREBASE_CREDENTIALS_PATH` / `FIREBASE_CREDENTIALS_JSON_BASE64` | Серверный service account Firebase | Должен быть предоставлен как секрет, никогда не коммитить |
| `FIREBASE_WEB_API_KEY`, `FIREBASE_ANDROID_APP_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_PROJECT_ID` | Публичная клиентская конфигурация Firebase | Настраивается для Android клиента; сама по себе не включает серверные credentials |

Для безопасного случайного секрета можно использовать команду на сервере:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

В клиентское приложение нельзя помещать `NAVIGATOR_TOKEN_SECRET`, пароли bootstrap, приватный Firebase service account или секрет API источника. Конфигурационная переменная в `.env.example` не означает, что она обязательна для каждого офлайн-сценария.

## 8. Источники школьных данных

Сервер поддерживает шесть коллекций с точным регистром имени:

- `Classes`
- `BaseSchedule`
- `Supplements`
- `Rooms`
- `Places`
- `Announcements`

### 8.1 Вариант JSON

Укажи:

```dotenv
NAVIGATOR_DATA_SOURCE=json
NAVIGATOR_DATA_JSON_PATH=/absolute/path/to/school-data.json
```

Структура верхнего уровня — объект JSON. Каждый ключ коллекции содержит массив объектов:

```json
{
  "Classes": [],
  "BaseSchedule": [],
  "Supplements": [],
  "Rooms": [],
  "Places": [],
  "Announcements": []
}
```

Этот пример показывает только контейнер коллекций; он не задаёт полноценную схему строк. Структура строк зависит от того, какие поля ожидают конкретные клиенты и API. До импорта школьных данных открой `assets/data/`, текущие тесты и соответствующие нормализаторы, затем согласуй названия полей, идентификаторы класса, дни недели, кабинеты и время занятий. Пустые массивы пригодны для проверки запуска, но не дают приложению реального расписания.

### 8.2 Вариант HTTPS API

```dotenv
NAVIGATOR_DATA_SOURCE=http
NAVIGATOR_DATA_API_URL=https://school.example.org/api
NAVIGATOR_DATA_API_TOKEN=CHANGE_ME
```

Сервер делает GET-запрос к `{NAVIGATOR_DATA_API_URL}/{CollectionName}`. Ответ принимается либо как массив объектов, либо как объект с ключом `data`, содержащим массив. Таймаут запроса в адаптере ограничен. Для удалённого источника нужен HTTPS; обычный HTTP разрешён только для loopback-разработки (`localhost`, `127.0.0.1`, `::1`).

### 8.3 Разделение данных и доступ

Публичные справочники ограничены allowlist и предназначены для данных, которые школа разрешила читать без входа. Индивидуальные данные ученика, полный список его ДОПов, привязки, устройства и аудит не должны публиковаться в публичном источнике. Документация серверной интеграции описывает Supplements как внутреннюю коллекцию; управляемый список индивидуальных занятий импортируется через авторизованные операции синхронизации.

Перед production проверь:
- источник содержит актуальные данные и корректные ID;
- неизвестные/пустые классы обрабатываются ожидаемо;
- время занятий корректно интерпретируется в часовом поясе школы;
- ответы источника не содержат персональных данных, не предназначенных для анонимного доступа;
- при недоступности источника API возвращает безопасную ошибку, а не внутренние пути/секреты.

### 9.2 Авторизованный API `/api/v2`

**Здоровье и конфигурация**

- `GET /api/v2/health` — общая проверка сервиса.
- `GET /api/v2/health/ready` — readiness check.
- `GET /api/v2/public/config` — несекретная клиентская конфигурация (например, параметры OIDC/Firebase).

**Аутентификация и сессии**

- `POST /api/v2/auth/login` — локальный логин/пароль; доступ к non-SSO login ограничен настройкой.
- `POST /api/v2/auth/sso` — проверка школьной OIDC-сессии и выдача сессии приложения.
- `POST /api/v2/auth/refresh` — обновление/ротация refresh-сессии.
- `POST /api/v2/auth/logout` — отзыв сессии.
- `GET /api/v2/auth/me` — текущий пользователь.
- `GET /api/v2/auth/permissions` — эффективные права пользователя.

**Администрирование аккаунтов, ролей и назначения**

- `POST /api/v2/admin/users`, `GET /api/v2/admin/users` — создание и просмотр аккаунтов в соответствии с правами.
- `PATCH /api/v2/admin/users/{user_id}` — изменение допустимых атрибутов/активности.
- `POST /api/v2/admin/sso-identities` — явная привязка SSO identity к аккаунту.
- `PUT /api/v2/admin/staff-positions`, `DELETE /api/v2/admin/staff-positions/{username}`, `DELETE /api/v2/admin/staff-positions/by-id/{user_id}` — назначение/снятие школьных должностей.
- `POST /api/v2/admin/student-links` — создание/изменение связи ученика по допустимым правилам.
- `POST /api/v2/admin/assignments`, `DELETE /api/v2/admin/assignments` — управление явными назначениями наставников/учителей.
- `POST /api/v2/management/users`, `GET /api/v2/management/staff` и `POST /api/v2/management/users/{user_id}/reset-password` — операции управления аккаунтами/сотрудниками по роли.

**Ученики, ДОПы, синхронизация и аудит**

- `GET /api/v2/students`, `GET /api/v2/students/{student_id}` — данные ученика только в пределах прав текущего пользователя.
- `GET /api/v2/management/students`, `GET /api/v2/management/students/{student_id}/supplements` — управленческий просмотр в допустимом охвате.
- `POST /api/v2/admin/students/{student_id}/supplements`, `POST /api/v2/management/students/{student_id}/supplements`, `PATCH /api/v2/management/supplements/{supplement_id}`, `DELETE /api/v2/management/supplements/{supplement_id}` — операции с индивидуальными ДОПами в соответствии с правами.
- `POST /api/v2/management/sync/supplements`, `POST /api/v2/management/sync/teacher-assignments`, `GET /api/v2/management/sync/status` — импорт/синхронизация и статус.
- `GET /api/v2/management/audit`, `GET /api/v2/admin/audit` — чтение журнала аудита с проверкой прав.
- `GET /api/v2/teachers/me/subjects` — назначенные текущему учителю предметы.

**Уведомления**

- `GET /api/v2/notifications` — лента текущего пользователя и доступные ему сообщения.
- `GET /api/v2/notifications/preferences`, `PUT /api/v2/notifications/preferences` — пользовательские настройки уведомлений.
- `GET /api/v2/admin/notifications`, `POST /api/v2/admin/notifications`, `DELETE /api/v2/admin/notifications/{notification_id}` — административное управление уведомлениями в пределах прав.
- `GET /api/v2/admin/notification-groups`, `GET /api/v2/admin/notification-groups/{group_id}/members`, `POST /api/v2/admin/notification-groups`, `POST /api/v2/admin/notification-groups/{group_id}/members`, `DELETE /api/v2/admin/notification-groups/{group_id}/members/{user_id}`, `DELETE /api/v2/admin/notification-groups/{group_id}` — управление адресными группами.

Для полного актуального списка маршрутов используй код роутеров `backend/school_api.py`, `backend/sso_api.py`, `backend/rbac_api.py`, `backend/notification_api.py` и OpenAPI-схему работающего экземпляра. Перед публикацией любого endpoint проверь его требования `Depends`, разрешения и фильтрацию записей по ученику/классу/назначению.

## 10. Аккаунты, роли и права

Есть две независимые оси полномочий:
1. **Базовая роль аккаунта** для базового доступа к сервису (например, `admin`, `student`, `mentor`, `teacher`).
2. **Школьная должность/назначение** в расширенном RBAC, которая даёт конкретные разрешения и может ограничивать класс или набор учеников.

Должность не делает каждого учителя суперпользователем. Назначения должны быть явно импортированы/подтверждены администрацией школы. Не сопоставляй учеников или учителей только по похожим именам.

Поддерживаемые школьные должности из исходников:

| Должность | Предназначение и границы (по модели прав в репозитории) |
|---|---|
| `director` | Школьный управленческий обзор, все ученики/ДОПы, управление сотрудниками и назначениями, публикация уведомлений, аудит |
| `deputy` | Академический/операционный обзор и управление в разрешённом наборе; не должен выдавать себе права суперпользователя |
| `homeroom_teacher` | Ученики и ДОПы закреплённого класса; классные сообщения |
| `teacher` | Доступ только к явно закреплённым ученикам/предметам и разрешённые адресные сообщения |
| `mentor` | Только закреплённые подопечные и соответствующие им данные/ДОПы |
| `mentor_coordinator` | Каталог учеников для назначений и управление наставническими/предметными назначениями |
| `dop_coordinator` | Справочник учеников, импорт/управление ДОПами и допустимые классные уведомления |
| `librarian` | Read-only доступ к каталогу учеников без автоматического доступа к персональному расписанию ДОПов |

Точный доступ должен проверяться по `PERMISSIONS` в `backend/rbac_api.py` и зависимостям endpoints на текущем commit. Таблица отражает намерение кода, не заменяет тестирование matrix доступа.

**Обязательные RBAC-тесты:**
- анонимный запрос не читает персональные данные;
- ученик не может читать другого ученика;
- учитель и наставник не могут выходить за явно назначенный scope;
- классный руководитель ограничен назначенным классом;
- координаторы получают только необходимые для их задачи полномочия;
- deputy не может выдавать себе director/admin-права;
- неактивная учётная запись/отозванная сессия не выполняет защищённые операции;
- все отказы корректно записываются и не раскрывают секреты.

## 11. Школьная авторизация OIDC

### 11.1 Общий поток

1. Клиент выполняет OIDC Authorization Code + PKCE через школьный identity provider.
2. Клиент получает OIDC tokens и отправляет `access_token` и `id_token` на `POST /api/v2/auth/sso`.
3. Сервер проверяет подпись/issuer/audience ID token по JWKS (или discovery), обращается к настроенному UserInfo endpoint и сверяет subject.
4. По умолчанию сервер принимает только явно привязанные к приложению subjects. Автоматическое создание/привязка пользователя отключены, если соответствующие настройки не включены.
5. После успешного связывания сервер выдаёт собственную прикладную сессию; дальнейшие операции проверяют серверный токен и разрешения.

Сам клиентский username/display name не должен считаться надёжным основанием для должности или прав.

### 11.2 Требуемая конфигурация

Поля на сервере задаёт школьный IT, среди них:
- `NAVIGATOR_OIDC_ISSUER`, `NAVIGATOR_OIDC_CLIENT_ID`;
- при необходимости `NAVIGATOR_OIDC_JWKS_URL`, `NAVIGATOR_OIDC_USERINFO_URL`;
- `NAVIGATOR_OIDC_REDIRECT_URI` (пример мобильного URI — `ru.pokolenie.navigator:/oauthredirect`);
- `NAVIGATOR_OIDC_DESKTOP_REDIRECT_URI` (в текущем примере — `http://127.0.0.1:43827/oauth/callback`);
- имена claims: username, display name, role, class ID;
- только по явному решению — автоматическая привязка/создание пользователей.

Desktop использует системный браузер и loopback callback. Зарегистрированный redirect URI обязан совпадать посимвольно с настройкой клиента у IdP.

### 11.3 Первоначальная настройка

1. Согласуй с IT безопасный issuer и клиент, redirect URIs, claims и тестовые учётные записи.
2. Запусти сервер с корректным `NAVIGATOR_TOKEN_SECRET` и bootstrap admin.
3. Создай/проверь аккаунт, привяжи точный стабильный OIDC `sub` через администратора (или используй заранее проверенную настройку initial director SSO subject).
4. Тестируй обычный ученический, teacher, mentor, director и административный сценарии на тестовых данных.
5. Проверь отзыв сессии, refresh rotation, невалидный issuer/audience, неизвестный subject и неактивную учётную запись.
6. Не включай auto-provisioning для admin по умолчанию. Разрешай его только при согласованном доверенном claim и тестовом подтверждении.

Локальный парольный вход для не-админов отключён по умолчанию. Переключатель `NAVIGATOR_ALLOW_NON_SSO_PASSWORD_LOGIN=true` требует явного решения школы и оценки рисков.

## 12. Объявления и уведомления

### Виды

Серверная модель уведомлений содержит типы `global`, `targeted`, `personal`, `dop_reminder`, `emergency` и виды адресации `all`, `class`, `group`, `user`. Право отправлять сообщения зависит от роли/должности и аудитории адресатов.

### Настройка и доставка

- Для очереди используется серверный worker, настраиваемый через `NAVIGATOR_NOTIFICATION_WORKER_ENABLED` и `NAVIGATOR_NOTIFICATION_POLL_SECONDS`.
- `NAVIGATOR_SCHOOL_TIMEZONE` используется для времени server-side reminders.
- Периодическая синхронизация расписания-derived teacher assignments и ДОПов задаётся `NAVIGATOR_AUTO_SYNC_INTERVAL_SECONDS`; значение `0` отключает периодический запуск.
- FCM необязателен и выключен в примере. После настройки service account, клиентской конфигурации и `NAVIGATOR_ENABLE_FIREBASE=true` пересобери Docker image.
- На Windows нативной сборке FCM не заявлен: клиент использует локальные toast-уведомления и, пока приложение запущено, опрашивает авторизованную ленту примерно каждые 45 секунд согласно README.
- Локальные напоминания о занятии требуют достоверного времени начала в данных. Не придумывай время там, где источник его не содержит.

Push — доставка best effort; необходимо тестировать retry, истечение сообщения, отключённые пользовательские предпочтения, недоступный Firebase, повторные попытки и дубль-уведомления. Не используй приложение как единственный канал экстренного оповещения.

Есть отдельные тестовые файлы для источников данных, импорта ДОПов, уведомлений, публичных объявлений, RBAC, школьного API, безопасности, SSO provisioning и синхронизации назначений учителей. Для Firebase при проверке соответствующего сценария потребуется отдельно установить `backend/requirements-firebase.txt`.

### 13.3 CI

Смотри `.github/workflows/flutter-ci.yml`, `.github/workflows/ios-build.yml`, `.github/workflows/ios-sign.yml` и `.github/workflows/publish-release.yml`. В workflow могут требоваться Repository Variables/Secrets. Сборка Android, сборка Windows, неподписанная iOS-сборка и подписанная IPA — разные сценарии. Секреты Apple signing, OIDC, backend и Firebase нельзя подменять публичным URL.

**При выпуске сохраняй evidence:** commit SHA, конфигурацию без секретов, результаты тестов/analyze, артефакт, его SHA-256 и запись о ручной проверке. Не делай вывод «всё прошло» только по наличию workflow.

## 14. Релиз, подпись и установка

### Android

- APK для теста можно собрать `flutter build apk --debug`.
- Для release сборки сначала убедись, какая signing config выбрана. В `android/app/build.gradle.kts` кастомная подпись из `android/key.properties` используется при её наличии; при отсутствии конфигурации код сейчас выбирает debug signing config.
- Debug-ключ нельзя считать production-ключом для публичного выпуска. Для реальной доставки настрой отдельный ключ, сохрани его вне Git, ограничь доступ и обеспечь резервное восстановление ключа/пароля.
- Не меняй release signing key между обновлениями установленной версии — иначе Android может отказать в обновлении приложения.
- Используй скрипт `setup_release_signing.bat` и инструкции его сопровождения, предварительно проверь его содержимое и созданные файлы.

### Windows

Установщик формируется на основе `windows/installer.iss`, если компонент Inno Setup доступен в сборочном окружении. Portable сборка должна включать EXE, соседние DLL и каталог `data`. README сборки предупреждает, что установщик может быть неподписан сертификатом издателя, поэтому Windows SmartScreen способен показать предупреждение.

### iOS

В репозитории есть отдельные workflow. Подписанная сборка требует актуальных Apple credentials и provisioning assets; эти секреты не нужны для Android-only сборки. Поддержка workflow не означает, что на каждом commit опубликован подписанный IPA.

## 15. Безопасность production

### Секреты и ключи

- Не коммить заполненный `.env`, пароли, токены, приватные ключи подписи или Firebase service-account JSON.
- Если секрет когда-либо попадал в историю Git, считай его скомпрометированным до ротации. Удаление файла в новом commit не удаляет значение из предыдущих commits.
- Серверный токен-секрет — случайный, как минимум 32 символа. Bootstrap password — минимум 14 символов.
- Ограничь доступ к env-файлам и бэкапам; не помещай серверные секреты в Flutter assets или Repository Variables, если они не предназначены для клиента.

### Сеть и API

- Публичный HTTPS reverse proxy, актуальные сертификаты и корректные headers; приложение FastAPI/Compose должно оставаться закрытым за reverse proxy.
- Ограниченный CORS через `NAVIGATOR_ALLOWED_ORIGINS`; не оставляй wildcard для production без доказанного основания.
- HTTPS для удалённого data source и OIDC. HTTP допустим только на loopback во время разработки.
- Включи rate limiting, мониторинг, резервное копирование и проверку восстановления на инфраструктурном уровне.
- Не публикуй индивидуальные ДОПы, данные аккаунтов, устройства, audit log или связи учеников в публичных endpoint.
- Проверяй, что серверная функция повторно проверяет разрешения для каждого объекта. Client-side check — только для UX.

### Персональные данные и школьная безопасность

- У школы должны быть утверждены правомерность обработки, круг доступа, сроки хранения и правила выгрузки/удаления данных.
- Используй обезличенные тестовые данные, если для теста не нужны реальные.
- Задай процесс отзывов аккаунтов/SSO links при уходе сотрудника или ученика.
- Уведомления могут не дойти; не заменяй ими официальную систему экстренной связи.
- Маршруты на карте не сертифицированы как эвакуационная схема. Их необходимо сверить с актуальными утверждёнными планами и ответственным сотрудником.

## 16. Известные ограничения и частые проблемы

### Приложение не загружает расписание с сервера

1. Проверь, что API URL указывает на правильный HTTPS origin.
2. Убедись, что сборка/настройка клиента знает API URL. Для CI используется repository variable `POKOLENIE_API_BASE_URL`, если workflow настроен на её чтение; это несекретный адрес, не место для токенов.
3. Проверь `NAVIGATOR_DATA_SOURCE`, путь JSON внутри процесса/контейнера, имена коллекций и формат массивов.
4. Выполни `GET /api/health` и проверь логи сервера. Не отправляй пользователю внутренние пути/секреты из подробной ошибки.

### Docker запущен, но источник JSON недоступен

Compose использует volume `navigator_data:/data`, но сам по себе не монтирует host file `school-data.json`. Убедись, что файл существует внутри контейнера на пути из `NAVIGATOR_DATA_JSON_PATH`, или переключись на корректный HTTPS data source.

### OIDC login не удаётся

- Сверь issuer, client ID, время системы, redirect URI и claims.
- Проверь, что issuer и endpoints используют HTTPS, IdP возвращает корректный JWKS/UserInfo, а `sub` привязан к правильной записи.
- Не пытайся исправить ошибку автоматическим linking по изменяемому имени пользователя.
- На Windows проверь регистрацию loopback callback URI и что порт не занят.

### FCM не отправляет push

- Убедись, что Firebase включён в .env **до** `docker compose up --build -d`.
- Проверь наличие service-account credentials как файла/секрета, реальные project ID и Android app ID.
- После смены build arg пересобери image; простого перезапуска старого образа недостаточно.
- Проверь серверную очередь и client permission/token registration. FCM не поддерживает заявленный нативный Windows сценарий.

### Android не устанавливает обновление

Вероятная причина — текущий APK подписан другим ключом. Проверь signing configuration и используй тот же надёжно сохранённый release key, что у установленной версии. Не распространяй production APK, подписанный временным debug key.

### Flutter/Gradle использует неправильный Java

Проверь `java -version`, `JAVA_HOME`, используемый Flutter JDK (`flutter doctor -v`) и toolchain 21 в Gradle. В рамках текущей конфигурации предпочтителен JDK 21.

### Тесты проходят локально, а реальные данные/маршруты ошибочны

Тесты проверяют только заявленные сценарии и test fixtures. Сверь карты с реальными планами, расписание с утверждённым источником и RBAC на отдельной тестовой базе. Не считай синтетический тест или скриншот доказательством пригодности маршрута.

## 19. Локальный ИИ, персональное расписание и категории помещений

Модель не включается в APK/EXE как большой asset. После установки пользователь может скачать Qwen2.5-0.5B-Instruct Q4_K_M (~398 МБ) в разделе локального ИИ-чата. Файл сохраняется в каталоге application support, скачивание выполняется во временный файл, перед активацией проверяются GGUF magic, минимальный размер и SHA-256. При несовпадении файл удаляется. Для модели не требуется Ollama или отдельный сервер: запуск выполняет `llm_llamacpp`.

Чат использует детерминированные команды для операций, затрагивающих данные. Модель может помогать с обычным диалогом и распознаванием навигационного запроса, но не является источником кабинетов, расписания или топологии коридоров. Для математических уроков парсер использует фактическое число математических слотов каждого дня:
- один названный предмет назначается всем математическим слотам выбранного дня;
- несколько названных предметов назначаются слотам по порядку времени;
- незаданные слоты становятся вопросом к пользователю;
- новые значения сначала показываются как черновик и сохраняются только после явного подтверждения;
- базовое расписание класса и предметы, не относящиеся к математическим слотам, не переписываются.

Навигационные команды распознают только ID из локального каталога помещений. Предпочтение «обходить кабинет» сохраняется локально и передаётся маршрутизатору как мягкий штраф для участков коридора вблизи точки. Рёбра настоящего графа не удаляются: если обойти помещение без разрыва пути нельзя, маршрут остаётся доступным, а приложение сообщает об ограничении. Замечания вроде «маршрут около 319 неверен» сохраняются отдельно для проверки карты. Автоматически перестраивать геометрию коридоров по свободному тексту небезопасно.

Каталог помещений разделяется на категории: учительские, администрация, математика, наука и лаборатории, информатика и технологии, гуманитарные, творческие, мастерские, спорт, медицина и поддержка, общие пространства и учебные кабинеты. Категория выводится из подписанного в каталоге назначения помещения; при изменении каталога классификатор можно дополнить.
