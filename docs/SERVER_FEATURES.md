# Серверные функции «Поколение» 0.2.0

Этот документ отвечает на практический вопрос: что сервер действительно умеет сейчас, что требуется настроить школе и что он пока не делает автоматически.

## Готовые серверные модули

| Область | Что реализовано |
|---|---|
| Учётные записи | Создание сотрудников и учеников, активация/деактивация, сброс пароля, отзыв сессий и устройств после изменения учётных данных |
| Роли | Технический администратор, директор, завуч, классный руководитель, учитель-предметник, наставник, координаторы ДОПов/наставников и библиотекарь; серверная проверка полномочий |
| Вход | OIDC SSO, серверные access/refresh-сессии, ротация refresh-токенов, выход с отзывом сессии |
| Ученики и назначения | Список учеников в назначенной области, привязка наставников и учителей к ученикам, ограничение доступа к личным ДОПам |
| ДОПы | Индивидуальные записи, изменение/удаление, импорт из настроенного источника данных и журнал результата синхронизации |
| Оповещения | Общешкольные, классные, групповые и личные уведомления; планирование отправки и срока действия; экстренный тип; лента уведомлений пользователя |
| Управление рассылками | Директор/завуч могут смотреть историю доставки и отменять ожидающие уведомления; уже доставленный push нельзя отозвать с устройства |
| Push | Firebase Cloud Messaging, регистрация/отзыв токенов устройств, повтор временных ошибок с ограниченным числом попыток |
| Напоминания | Серверные напоминания о ДОПах за 15 минут до начала только при согласии ученика и корректном времени занятия |
| Аудит | Журнал важных действий и результатов доставки |
| Готовность | Health/readiness проверки источника данных, секретов и конфигурации SSO/Firebase |
| Источники данных | Локальный JSON-файл или HTTPS API; разрешённые публичные коллекции только для чтения |

## Первый технический администратор и директор

Технический администратор создаётся при первом запуске из NAVIGATOR_BOOTSTRAP_ADMIN_USERNAME / NAVIGATOR_BOOTSTRAP_ADMIN_PASSWORD, если в базе ещё нет ни одной учётной записи с ролью `admin`. Существующую отключённую учётную запись автоматически не активирует и не пересоздаёт.

Первый директор также может создаваться конфигурацией сервера:

- POKOLENIE_BOOTSTRAP_DIRECTOR_USERNAME
- POKOLENIE_BOOTSTRAP_DIRECTOR_PASSWORD (не менее 14 символов)
- POKOLENIE_BOOTSTRAP_DIRECTOR_DISPLAY_NAME (необязательно)
- POKOLENIE_BOOTSTRAP_DIRECTOR_SSO_SUBJECT (необязательно, стабильный sub школьного IdP)

Если директора ещё нет, сервер создаст сотрудника с должностью director. Повторный запуск не сбрасывает существующий пароль и не создаёт дубликаты. Если указан SSO subject, он привязывается к NAVIGATOR_OIDC_ISSUER; конфликт существующей привязки останавливает bootstrap, а не меняет владельца учётной записи.

По умолчанию локальный парольный вход для директора выключен: настрой SSO и укажи его точный SSO subject при bootstrap либо свяжи аккаунт после запуска через технического администратора (POST /api/v2/admin/sso-identities). Если subject не указан, обязательно создай и настрой технического администратора через `NAVIGATOR_BOOTSTRAP_ADMIN_USERNAME` и `NAVIGATOR_BOOTSTRAP_ADMIN_PASSWORD`, иначе некому будет выполнить привязку SSO. Не включай локальный вход для всех сотрудников только ради упрощения настройки.

## Общешкольное уведомление

Директор или завуч публикует общешкольное сообщение через POST /api/v2/admin/notifications с kind="global" и target_type="all". Все авторизованные активные аккаунты видят это сообщение через GET /api/v2/notifications; экран «Оповещения» загружает авторизованную ленту и сохраняет ограниченный кеш для офлайн-просмотра.

Если Firebase настроен, фоновый worker доставляет push на зарегистрированные устройства. Если Firebase не настроен, лента API продолжает работать, но push не отправляется. Проверяй push_status, delivery_status и delivered_count через GET /api/v2/admin/notifications?limit=100.

Для отмены запланированной или ещё не начавшейся доставки используй DELETE /api/v2/admin/notifications/{id}. Если push уже доставлен, сервер может скрыть запись из in-app ленты, но не способен убрать уведомление с чужого телефона.

## Что нужно предоставить школе

1. Постоянное хранилище SQLite и HTTPS reverse proxy.
2. Случайный NAVIGATOR_TOKEN_SECRET и сильный bootstrap-пароль технического администратора.
3. Подтверждённые школой OIDC issuer/client/redirect URI и правила соответствия учётных записей.
4. Источник данных школы в документированном JSON-формате либо API с HTTPS и соответствующими колонками.
5. Firebase server credentials и клиентская конфигурация, если нужны push-уведомления.
6. Настройки резервного копирования, сроков хранения данных, мониторинга и ограничения частоты запросов.

## Что не включается само по себе

- Настройки OIDC и Firebase не включаются в репозиторий: их выдаёт школа/оператор инфраструктуры.
- Формат реального школьного расписания и intranet необходимо сопоставить с контрактом источника. Код не может угадать частную схему.
- Публичные endpoint'ы источника — read-only; изменение школьного расписания выполняется в настроенном источнике. Индивидуальные ДОПы и данные аккаунтов управляются API.
- Сеть доставки push — best-effort; приложение не заменяет официальную систему экстренного оповещения.
- Автотесты маршрутов не сертифицируют безопасные или эвакуационные пути.
